# Bitwig ステップ入力の調査結果 (6.1.7)

`step-input-arrow-advance` を作るときの検証結果と考察。調査に使ったトレース mod と生ログは削除済みで、ここには残す価値のある結論だけを書く。

## Bitwig 標準の挙動

ステップ入力ツールでは、押したキーを「最初のキー押下から最後のキー離しまで」を 1 グループとして扱う。

- 最後のキーを離すと、カーソルが 1 ステップ進み、保留中のノートがそこまで伸ばされて書き込まれる (オートアドバンス)。
- 「Move Time Selection One Step Later」(→) をキー保持中に使うとノートを伸ばせるが、離したときの**オートアドバンスが飛ばされる**。結果、ノートもカーソルも想定より 1 ステップ短い。
- 最後のキーより 120 ms 以上前に離したキーは**落とされる** (コード時間)。
- 保持中に ← (Move Time Selection One Step Earlier) を使うと、ステップバックして削除する。このとき離したキーは何も書かない。

## 検証したケース (グリッド 1/16、カーソル 0 から)

| 操作 | Bitwig 標準 | mod あり |
|---|---|---|
| C を押して離す | C 0-16、カーソル 16 | 同じ |
| C を押しながら →、C を離す | C 0-16、カーソル 16 | C 0-32、カーソル 32 |
| C を押しながら →、E を押して離し、C を離す | C 0-16、E 16 長さ 0、カーソル 16 | C 0-32、E 16-32、カーソル 32 |
| C と E を押し、C を離し、後で E を離す | E 0-16 のみ | C 0-16、E 0-16、カーソル 16 |
| C と E を押し、→、C を離し、後で E を離す | C 0-16、E 0-16、前進なし | C 0-32、E 0-32、カーソル 32 |
| C と E を押し、C を離し、→、E を離す | コードとして書かれない | C 0-16、E 0-32、カーソル 48 |
| C を押しながら ← で戻り、離す | 何も書かない | 同じ (標準のまま) |

→ を 1 回増やすごとに 1 ステップずつ伸びる。

## 設計上の結論

- **タイミングで判断しない。** 時間差で判断すると、ほぼ同時に離したコードが分割される (`E3/C2C` のように最後の 1 ステップが別ノートになる)。押したキーの状態 (保持中のキー、離した時点のカーソル) だけで決める。
- 最後以外のキーを離した時点で、そのときのカーソルを記録しておく。最後のキーを離したとき、カーソルがその後動いていなければ通常の前進に合流し、動いていればそのキー自身の前進分の長さで書き込む。
- 「キーを離したときの前進」は、グリッドの次の線 (`input.ZRB().VNw().unz(cursor + 0.001)`) で求める。Bitwig 自身の前進と同じ。
- ← のあとは Bitwig の元の動作 (離したキーは何も書かない) に任せる。これを壊すと「消すために押していたキーが追加される」問題が出る。
- 書き込みの重複を避けるため、書いたばかりのキーと保留済みのキーは、Bitwig が再び保留に追加しないよう `List.add` を差し替えて止める。

## 調査の手法 (再現用)

- 何が呼ばれているかは、コードを持たない**トレース専用 mod** で見た: 対象クラスのメソッドを列挙してトレースフックだけを定義し、Debug Mode を ON にして `sessions/<id>/traces/trace.tsv` のスタックを読む。
- 見るべきクラス (6.1.7 の名前): `bjW` (ステップ入力: 保持キー `Anf`、保留ノート `unz`、カーソル `sCA()`)、`bjv` (時間選択のキーアクション)、`DrA` (ノート挿入)、`eet` (ステップ入力の有効/無効)。
- Debug Mode が OFF のセッションは何も記録されず、検証に使えない。
